Thread-Safe Memory Concurrency
Java
private static final ConcurrentHashMap<String, String> sessionUsernames = new ConcurrentHashMap<>();
private static final ConcurrentHashMap<String, Session> clientSessions = new ConcurrentHashMap<>();
private static final Set<Session> librarianSessions = Collections.synchronizedSet(new HashSet<>());
The Design Strategy: You are using thread-safe data structures (ConcurrentHashMap, Collections.synchronizedSet) explicitly declared as static across the application container scope.

Why It Matters: WebSocket connections are highly asynchronous;
 hundreds of users can open connections, close windows, or send data frames at the exact same millisecond.
 Using basic arrays or standard HashMaps would instantly trigger a ConcurrentModificationException or result in memory leaks.
 Your layout guarantees thread safety across separate connection threads without locking up the server.


 What Do "Ping" and "Pong" Actually Do?
 Java
 if ("ping".equals(message)) {
     try { session.getBasicRemote().sendText("pong"); } catch (IOException ignored) {}
     return;
 }
 This tiny block of code solves a major real-world networking problem: Silent Disconnections (Ghost Connections).

 The Problem: TCP Idle Timeouts & Firewalls
 When a student opens a chat tab but doesn't type a message for a few minutes, the connection becomes idle. Network routers, firewalls, and cloud providers (like AWS or Heroku) hate idle TCP connections because they waste resources. If a connection stays silent for too long (often 30 to 60 seconds), firewalls will silently terminate the connection without telling either the server or the client.

 To the server, the session looks open, but any message sent into it disappears into a black hole.

 The Solution: The Heartbeat Mechanism
 To prevent idle timeouts, the client application is programmed to send a small, lightweight text frame—"ping"—every few seconds.

 Keep-Alive: Sending a message resets the idle timeout clock on every router and firewall along the way, keeping the tunnel open.

 The Pong Acknowledgement: When your server interceptor sees "ping", it instantly echoes back "pong". This tells the client browser, "The server is alive and listening."

 Low Overhead: By using an immediate return; statement, you bypass all the heavy chatbot logic, regex parsing, and librarian broadcast loops.
 The ping/pong exchange happens completely in memory in less than a millisecond.
